# План экспериментов по рекомендациям дополняющих товаров

**Статус:** рабочий план команды. В репозитории есть подготовка, аудит и разбиение четырёх датасетов. Сравнение моделей предстоит запустить. Первый пилот проводим на Amazon Musical Instruments.

**Задача:** по исходному товару и заданной целевой категории выдать топ-10 товаров этой категории. Главный вопрос — помогают ли совместные просмотры предсказывать отложенные совместные покупки, особенно при нехватке покупок. Совместная покупка служит приближённой разметкой дополняемости. [Постановка проекта](../README.md)

### Модели и контролируемые различия

- **MostPopular** ранжирует товары целевой категории по числу входящих обучающих buy-связей. Популярность пересчитываем для каждой доли покупок.
- **Двухбашенные модели** оценивают запрос «товар + целевая категория» и кандидата. Buy-only использует покупки, Mixed объединяет покупки и просмотры, Shared учит общий энкодер с отдельными парами голов для `buy` и `view`, Pretrain → Buy учится сначала на просмотрах, затем на покупках. Для Shared на выдаче используем buy-головы. В основном сравнении фиксируем доступные признаки и бюджет настройки. Для Transformer токен `[BUY]` задаёт тип связи при выдаче.
- **Tucker 3D** использует одну таблицу товарных векторов и балл \(s(i,j,r)=u_i^\top M_r u_j\). При двух типах связей и полном ранге по оси отношений напрямую обучаем две матрицы \(M_{\mathrm{buy}}\) и \(M_{\mathrm{view}}\). По форме оценки это RESCAL. В контроле `buy-only` убираем ветвь просмотров, сохраняя ранг и buy-данные. В обоих случаях на выдаче используем \(M_{\mathrm{buy}}\); целевая категория задаёт множество кандидатов. [RESCAL](https://icml.cc/2011/papers/438_icmlpaper.pdf) · [Tucker с общими факторами](https://proceedings.mlr.press/v238/peshekhonov24a.html)
- **DistMult** заменяет каждую полную матрицу \(M_r\) диагональной. Сначала сравниваем с Tucker при одинаковой размерности товарных векторов. **CP** сохраняет покоординатную оценку, но использует разные таблицы для источника и кандидата. Если CP выигрывает, повторяем сравнение при близком числе параметров, чтобы понять вклад размера модели. [DistMult](https://arxiv.org/abs/1412.6575) · [CP](https://proceedings.mlr.press/v80/lacroix18a.html) · [ComplEx](https://proceedings.mlr.press/v48/trouillon16.html)
- **Графовый бейзлайн.** Строим разреженные матрицы обучающих связей \(B\) и \(V\) и нормируем строки по числу исходящих связей. Балл контроля — \((B^2)_{ij}\). Балл с просмотрами — \([B^2+\lambda(BV+VB)]_{ij}\). Выбираем \(\lambda\) на validation, сохраняя фиксированный коэффициент при \(B^2\). Считаем пути только для нужных запросов по спискам соседей или разреженным умножением. Пример `view→buy`: гитару смотрят вместе с похожей гитарой, которую покупают с чехлом. Это адаптация идеи путей из MMSC под наши текущие данные и ранжирование внутри категории. [MMSC, SIGIR 2026](https://arxiv.org/html/2507.22268v3)
- **HOSVD** получает факторы из разреженных развёрток обучающего тензора. Оставляем одинаковые товарные ранги с Tucker, исключаем holdout при построении входа и ранжируем по восстановленному слою `buy`. Стандартный HOSVD вычисляет товарные факторы отдельно и приближает тензор с нулями на ненаблюдаемых ячейках. Сравнение с градиентным Tucker поэтому включает различие факторов и цели обучения. [HOSVD](https://epubs.siam.org/doi/10.1137/S0895479896305696)
- **MIG-TF** добавляет гиперболический компонент к тензорной оценке. Сравниваем с обычным Tucker на тех же тройках и при близком размере модели. У опубликованной работы результаты на графах знаний, поэтому перенос на `buy/view` — отдельная гипотеза. [MIG-TF, AISTATS 2025](https://proceedings.mlr.press/v258/yusupov25a.html)

## Общий протокол

1. **Данные.** Последовательность воспроизведения — [подготовка](../datasets/dataset_preparation.ipynb), [аудит](../datasets/dataset_analysis.ipynb), [разбиение](../datasets/dataset_splitting.ipynb). Подготовка скачивает источники Amazon 2018 и Kaggle. Зависимости в ноутбуках: `pandas`, `kagglehub`, `matplotlib`, `numpy`. Входы для моделей лежат в `data/splits/seed_42/<dataset>/` и каталоге из `data/processed/`. Для каждого запуска сохраняем версию и состав каталога. Цель пилота — до 20 тыс. товаров на одном GPU Kaggle, с единым каталогом для всех запусков пилота.
2. **Защита от утечек.** На Amazon используем готовый split с seed 42. Пара и обратная пара попадают в одну часть. Validation/test пары исключаются из обучающих `buy` и `view`. В исправленной серии наши градиентные модели выбирают negatives по доступному train. В исторических Amazon-контролях Buy-only и Shared список отложенных пар также использовался для их исключения из negatives. Граф строим только из разрешённых обучающих связей. Журналы событий делим по времени, сессии и транзакции на границах исключаем целиком. Там повторная пара в разных периодах возможна по протоколу. Для 3D агрегируем пользовательскую ось, для 4D сохраняем `user_id` и оцениваем обе модели на одном наборе известных пользователей.
3. **Разреженность.** Вложенные подвыборки покупок строим по ключам пар, удерживая прямое и обратное направления вместе. Сохраняем seed и состав каждой доли. Между долями фиксируем `view`, каталог, validation/test и оцениваемые запросы. В отчёте указываем фактическое число связей и долю оцениваемых товаров, потерявших все обучающие покупки.
4. **Обучение.** Для градиентных разложений используем BCE на наблюдаемых и выбранных ненаблюдаемых парах. Для контроля эффекта просмотров фиксируем buy-примеры, способ подбора ненаблюдаемых пар, размер эмбеддингов и бюджет обновлений по buy. При совместном обучении вес вспомогательной задачи выбираем по validation. Ранг и остальные гиперпараметры подбираем по validation при сопоставимом бюджете. Для финальных градиентных запусков используем три согласованных seed и показываем среднее и разброс.
5. **Оценка.** Запрос — `(source_item, target_category)`. Релевантные товары — отложенные buy-кандидаты этого запроса. Используем единый список кандидатов из целевой категории и одинаковую обработку исходного товара, известных тренировочных покупок и равных баллов. Фиксируем маску уже известных покупок в оценщике для всех долей, вычисляя её из полного train. В модели передаём только связи выбранной доли. Сохраняем число запросов, кандидатов и покрытие после фильтров. Публикуем Recall@10, NDCG@10 и HitRate@10 по запросам, число параметров, время обучения и время выдачи на одном оборудовании. Время Pretrain → Buy включает обе стадии, а для графового метода отдельно учитываем подготовку графа.
6. **Интерпретация.** Для каждого сравнения считаем разницу метрик на одних и тех же запросах. Для разреженности сравниваем разрыв между `buy+view` и `buy-only` при разных долях, поскольку абсолютное качество может падать у обеих моделей. Для гипотезы о сопоставимом качестве Tucker и Shared задаём допустимое отклонение Recall@10 и NDCG@10 до финального теста. Сравнение нейросетей с Tucker учитывает использование товарных признаков, а внутримодельные сравнения изолируют добавление просмотров. Удачные и ошибочные рекомендации из топ-10 проверяем вручную как примеры совместимости. [Allegro, RecSys 2025](https://arxiv.org/abs/2508.03702) · [AlleCompanion, OARS 2026](https://arxiv.org/html/2609.05063v1)
